# Grill Me — 需求到 Issue

基于 Matt Pocock 的 `grill-me` / `grilling` 改编。来源、固定版本与改动范围见 [SOURCE.md](SOURCE.md)，许可见 [LICENSE](LICENSE)。本文件内含所需访谈逻辑，无需安装另一个 `grilling` skill。

## 规范与任务范围

开始时读取[需求到 Issue 流程](../../../docs/workflow/requirement-to-issue.md)和[Issue 模板](../../../docs/templates/development-issue.md)。这些链接相对于本 skill 文件解析，目标业务项目的事实和约束从该项目读取。身份存在疑问时再读取[稳定标识体系](../../../docs/traceability/identity-system.md)。不要复制这些文档形成另一份规则。

本 skill 的交付物是需求共识和 Issue 草稿；设计、实现或发布只在用户授权范围内继续。对话、文档、截图、缺陷和已有任务均可作为输入。用户仅要求评估方案时，交付澄清结论，不强制创建任务。

## 构建决策树

先读取输入和足以理解任务的项目上下文，区分原始要求、已确认共识、当前实现事实、假设与疑问。已有任务直接补齐，不另建重复草稿。

将缺口组织为决策树：一个决定会引出依赖它的后续决定。围绕本次目标检查参与者、触发、成功状态、业务规则、异常、范围及验收条件；只展开会影响本次任务的分支。

查找事实是你的工作。能从已有文档、代码和工具查明的事情先查，不让用户重复提供。当前代码只能证明当前行为，不能替代业务预期。查不到时明确证据缺口；不猜测微服务归属、权限规则或产品结论。不要求子代理；只有当前会话允许时才可委派事实查找。

## 按依赖分轮追问

每轮选择前置条件已经明确的问题。答案依赖其他未决问题的，放到后续轮次；独立问题可以同轮提出，但按影响排序，控制每轮认知负担。

对每个问题给出：具体情境、需要决定的行为、建议及理由。没有足够依据时说明无法推荐，不为凑选项制造结论。建议始终是建议，不是用户确认。

等待用户回答后再展开依赖该回答的分支。可以同时推进不依赖回答的资料查找和草稿整理；不能把超时或未回答视为同意。遵循当前环境的提问工具与会话规则。

例如：不能先假定同步必须整体成功，再询问整体回滚的实现方式。应先明确业务上允许的成功与失败结果。

## 每轮沉淀到草稿

每次得到答案后，更新同一份任务草稿：

- 已确认共识及确认人或来源、时间；无法取得的信息明确缺失，不补造。
- 对应的用例流程、拟议业务规则和可观察的 AC。
- 已解决问题、仍待确认问题，以及其影响的工作。
- 关键结论改变时的原因及受影响 AC，保留依据。

例如，用户确认“无序多选仅改变顺序不算变化”后，将其整理成比较规则，并形成 `[A,B]` 改为 `[B,A]` 不新增记录的 AC。不要把对话仅压缩成无业务映射的摘要。

草稿可先在项目约定的本地位置或对话中提供可复制 Markdown。远程 Issue 支持 GitHub / GitLab，读取和写入分别使用 `gh` / `glab` 命令行；操作前读取[Issue 命令行操作](../../../docs/workflow/issue-cli.md)，按其规则确认目标、处理正文和核对结果。CLI 不可用时保留草稿与阻塞原因，不自行切换其他操作通道。

上下文交接前给出当前草稿位置或实际 Issue URL、未决问题和下一步。写入远程 Issue 需要用户已有授权；仅请求澄清不等于授权发布。有授权和可用 CLI 时直接执行并读取核对结果，避免重复创建。发布后以远程 Issue 为任务正文的权威位置。

## 收敛并输出 Issue

关键决策树已收敛，且满足规范中“进入实现前”的条件时，停止扩展问题，按模板输出可进入设计的草稿。复用用户已经给出的确认，不额外设置固定的最终审批轮次。

如用户提前结束或关键问题尚无答案，输出待澄清草稿，明确阻塞范围，不能宣称需求就绪。超出本次范围的分支记录范围结论，不无限追问。

依据规范按主要用例拆分业务 Issue，复用已有 UC / BR 身份，未核对的编号标记拟议。多个用例需要整体验收时给出父任务及需求点到子任务 / AC 的覆盖关系；不要按 Controller、数据库和测试分别创造业务用例。Bug 和技术任务使用模板的适用栏目。

在输出前核对：每条 AC 有独立依据；关键疑问未被静默当成规则；原始需求点有对应任务或明确范围结论；跨仓库依赖已识别或标明未知。设计和验证栏目只写已知方案或计划，不编造类实现、提交、Issue 编号或 PASS 证据。
