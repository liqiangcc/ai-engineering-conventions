# Issue 工作计划与查找

## 目的

使用计划 Issue 组织一周、一次迭代或一个交付目标，使用研发 Issue 推进具体工作。计划维护目标、优先顺序和安排，任务维护执行状态，避免手工同步两份进度。

## 计划与任务

- 使用[工作计划模板](../templates/work-plan-issue.md)，标签为 `类型：工作计划`。只有需要组织多项工作时才创建计划，单个任务可以直接执行。
- 计划正文记录目标、计划周期或目标日期、任务完整 URL、优先顺序、依赖和时间约束。日期是计划，不是交付证据。
- 任务沿用[研发 Issue 模板](../templates/development-issue.md)和[中文阶段标签](issue-progress.md)。负责人使用平台已有分配字段；不在计划中抄写任务阶段、完成百分比或人工勾选的完成清单。
- 工作计划不强制套用研发阶段标签。是否开放使用平台状态，阻塞可按实际情况标注并说明原因。若计划本身就是已有需求父任务，直接复用该 Issue，不另建重复计划；承担研发验收的父任务继续遵守研发阶段约定。
- 跨仓库计划选择一个明确的承载仓库，引用各仓库任务完整 URL。计划归属不意味着所有代码都在该仓库实现。

## 调整与收尾

新增、延期、移出或调整优先级时，更新当前计划并保留原因和确认依据。依赖中的研发任务继续在原 Issue 推进，不因跨周重新创建。

计划收尾时核对关联任务的交付证据及本期目标，区分已完成、未完成和取消。周期结束不代表工作已完成：未完成项应有明确后续安排或下一期计划链接。可以在记录本期结果及剩余工作去向后关闭周期计划，但不得把顺延事项报告为已交付。

## 查找与当前结论

- 研发任务标题采用“业务对象：动作”，例如“数据处理者：新增变更时间轴”；计划标题采用“周期或目标：工作计划”。让标题包含可检索的业务词，不只写“优化”“修复问题”。
- 通过平台状态、中文标签、负责人、标题关键词和时间筛选，进入 Issue 后沿任务、MR / PR、提交与证据链接继续查找。查询和更新都按[Issue 命令行操作](issue-cli.md)执行。
- 正文维护当前结论，评论保存关键讨论及变更依据；用户确认后及时更新正文，不能要求后来者从全部评论猜测哪个结论生效。
- 术语、业务规则和设计共识可先保存在任务 Issue，无需同时创建术语文件、BR 文档或 ADR。拟议结论、已确认要求和已生效规则应明确区分，必要时注明适用业务上下文及版本。
- 当多项任务反复引用同一知识且当前定义难以定位时，再按需提取到长期知识 Issue；其他任务引用完整 URL。不要为每条规则预先建立一个 Issue。
- 同一规则只有一个明确的当前定义位置。发生替代时，旧位置指向新位置并保留历史依据；已有项目权威规则、接口契约、环境配置和验证命令继续引用原位置，不为采用 Issue 搬迁或复制。

计划、任务和知识记录的区分用于确定维护责任，不要求增加层级或另建管理台账。
