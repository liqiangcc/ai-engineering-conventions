# 复杂度预算

## 目的

关注点分离的目标是降低认知复杂度，不是最大化抽象数量。

每增加一个层、接口、包、标识或文档，都消耗复杂度预算。只有当它降低了更大的变化成本、理解成本或风险时，才值得保留。

## 什么时候值得建立新边界

满足以下至少一项时 SHOULD 考虑拆分：

- 两部分变化原因明确不同；
- 需要独立单元测试；
- 存在真实的替换需求；
- 一边含外部副作用；
- 属于不同安全边界；
- 故障类型需要分开处理；
- 单个文件已混合多个业务动作；
- AI / Reviewer 为修改局部逻辑必须阅读大量无关代码。

## 什么时候不应继续拆

以下情况 SHOULD 保持简单：

- 只有几行稳定代码；
- 新接口只有一个实现且没有形成边界价值；
- 拆分后所有文件仍然总是一起修改；
- 新类只是转发调用，没有独立语义；
- 只是为了符合某个架构图；
- 需要不断在多个极小文件之间跳转才能理解一个简单行为。

## AI 主导项目的取舍

AI 降低了样板代码的生成成本，因此可以比纯人工项目接受更强的一致性，例如：

```text
一个 Operation
→ 一个明确 Use Case
→ 独立测试
```

但 AI 并没有消除认知复杂度。大量没有语义价值的 Factory、Provider、Impl、Manager、Helper 仍然会增加检索噪声。

因此本规范优先接受：

```text
重复但可预测的结构
```

拒绝：

```text
抽象但不可预测的结构
```

## 判断公式

新增抽象前问：

```text
新增结构成本
<
它减少的变化耦合 + Review 成本 + AI 搜索成本 + 测试成本 + 故障风险
```

如果不能解释新边界隔离了哪一种变化原因，就不应该创建该边界。

## 默认策略

- 业务模块：强边界；
- 复杂状态变更 Use Case：独立；
- 业务规则：显式；
- 外部技术：通过 Port / Adapter 隔离；
- 简单值对象：保持简单；
- 无业务语义的转发层：避免；
- 通用 `Utils` / `Helper` / `Manager`：默认不允许；
- 自动生成的样板：允许存在，但必须保持可预测。
